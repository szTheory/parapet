<objective>
Add a `check_recovery` static check to `mix parapet.doctor` that reports a recovery-action adoption signal (ADOP-02): the count of attached capabilities, warnings for runbook steps referencing unregistered capabilities, and a per-capability host-module/callback health check (D-11, D-12). It slots into the existing harness contract (`%{status:, messages:}`) with zero harness changes and is kept SEPARATE from `check_runbooks` (D-13).

Purpose: Give adopters a self-serve adoption signal without making the doctor a hostile gate. Adoption ABSENCE is a nudge, not a failure — so zero capabilities is `:skip` (A1 resolution; see decision note below), never `:error`, and never `:warn` (which would fail `--ci` because the `--ci` threshold is `:warn` at doctor.ex:54).

Output: `check_recovery` + its `@static_checks` registration + dispatch clause in `lib/mix/tasks/parapet.doctor.ex`; six Wave-0 signal-condition cases in `test/mix/tasks/parapet_doctor_test.exs`.

**A1 DECISION (zero-capability status = :skip, NOT :warn):** CONTEXT.md D-12 literally says "zero attached capabilities is :warn". But the `--ci` threshold defaults to `:warn` (doctor.ex:54) and `:warn` findings FAIL CI — which would make `mix parapet.doctor --ci` fail on every fresh adopter install, directly contradicting CONTEXT.md's own stated invariant ("a fresh install with zero capabilities still passes --ci"). Per CONTEXT.md "Claude's Discretion" (which delegates exact status thresholds) and RESEARCH.md Assumption A1, zero attached capabilities → `:skip`, matching the existing `check_runbooks` no-SLOs precedent (doctor.ex:106) and `check_cardinality` no-SLOs precedent (doctor.ex:239). `:warn` is reserved for genuinely-broken states (unregistered-capability-in-runbook; missing host module/callback). A URL-valued runbook is a SKIP, never an error.
</objective>
