## Cross-Phase Integration

**Verdict: WIRED end-to-end with 4 presentation/docs warnings. No broken flows.**

E2E recovery loop — per-handoff trace (all connected):

1. Host declares `Parapet.Recovery` module → `attach/1` at boot (demo application.ex:19) → `Capabilities.register_recovery/2` (supervised Agent, not Application env). **WIRED**
2. Runbook step references capability atom → `Capabilities.get_recovery/1` resolves it (operator.ex). **WIRED**
3. Preview → 5-min token + target_refs/warnings stored in `recovery_preview` TimelineEntry. **WIRED**
4. Preview panel token → Confirm handler (`phx-value-token` ↔ handle_event param names match). **WIRED**
5. `confirm_runbook_step/4` → `ClaimService.claim_action/1` (`action_kind: "operator"`, 5-min lease). **WIRED**
6. `{:won}` → `capability.execute/2` (try/rescue) → `mark_executed` / `mark_failed`. **WIRED**
7. Success → `recovery_confirmed` TimelineEntry + `ToolAudit` in one Ecto.Multi. **WIRED**
8. Failure → `recovery_failed` TimelineEntry; short-circuit/conflict write nothing (structurally enforced). **WIRED**
9. Retrospective renders both entry types inline. **WIRED**

Warnings (all in tech_debt above): (1) UI-01 panel omits target-args + diff; (2) timeline body generic fallback for recovery types; (3) CHANGELOG v1.1.0 section not yet present (expected — release-please generates at tag); (4) 9 templates generated vs 6 documented.

## Recommendation

Status is `tech_debt`, not `gaps_found`: nothing blocks the milestone's core value (a safe, claim-protected, audited Preview → Confirm loop that an adopter can generate and run). The debt is real but optional-to-close, and most of it is display polish or process artifacts.

Two items are worth a deliberate decision before close, both adopter-visible:
- **UI-01 preview panel** — add target-args list + a diff/summary to the generated panel (and a CI assertion stronger than the title substring). This is the gap an operator would feel.
- **`attach/1` hardening on a Stable surface** — add `function_exported?/2` + rescue around host `id/0`/`label/0`, or explicitly accept the carry-over and document it, since the module is now Stable.

Everything else (WR-WR0x copy/taxonomy, timeline body, REQUIREMENTS/SUMMARY bookkeeping, Nyquist artifacts, template count) can be batched into a single cleanup phase or accepted into the backlog.
